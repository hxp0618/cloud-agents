Infrastructure Architecture Design

Cloud Workspace / Sandbox 基础架构设计

第一阶段共同交付长期云工作区、通用 Sandbox、客户节点接入与完整 Admin Web；基础设施与对应管理界面一起验收。 用户侧 CloudAgents 在底座验收后消费这些能力。OpenSandbox 是待固定版本验证的首选执行基础候选， Workspace、访问授权、RemoteWorker 接入、调度、计量和多租户权威仍由平台掌握。

1. 执行摘要

最终架构不是“把 OpenSandbox 套一层网页”，而是由四个相互解耦的平面组成： 用户体验平面、SaaS 业务平面、核心控制平面、区域执行/数据平面。OpenSandbox 是运行协议和部分执行组件， 不会直接暴露给终端用户，也不会成为 SaaS 数据模型的唯一来源。

两套 Web，两个安全边界
User Web 面向租户；Control Plane Web 面向管理员。域名、API、身份客户端、权限和发布流水线分开。
Workspace ≠ Sandbox
Workspace 是长期资产；Sandbox Session 是一次可替换运行实例。删除实例不等于删除代码和数据。
Provider ≠ Runtime
Provider 表示资源位置；Runtime 表示隔离方式。同一 Hetzner 裸金属节点可运行 runc、gVisor、Kata 或 MicroVM。
平台节点与客户节点并存
平台自有 Region 与 BYOC/BYON/Edge/IDC 统一通过 Region Controller 和 Remote Worker 接入。
当前主线：BASE-M0 验证候选与领域映射 → M1 长期 Workspace/异步生命周期 → M2 Exec/PTY/Files/Preview/SSH → M3 outbound 客户节点 → M4 Kubernetes/容量/强隔离矩阵 → M5 文件系统快照、独立交付与运维 → BASE-READY → APP-M1 用户 CloudAgents。 Admin Web 与对应基础设施能力共同完成；no-Agent 不等于无管理界面。安全从首个入口落实。Direct MicroVM、内存快照、Warm Pool、跨 Region 调度和商业账单后置。

2. 目标、范围与非目标

业务目标
  • 用户可从 Web、Desktop、CLI、SDK、SSH 创建和进入 Coding Workspace。
  • 支持 Codex、Claude Code、OpenCode、VS Code Server、浏览器与常用开发工具链。
  • 支持平台托管与客户自带计算节点，并对底层云厂商和 Runtime 做产品化抽象。
  • 支持组织、项目、配额、计量、审计、密钥、持久卷、快照和网络策略。
  • 对不可信 Agent 代码提供分级隔离与默认安全网络。
技术目标
  • 统一 Sandbox 生命周期、Exec、PTY、Filesystem、Volume、Port、Event API。
  • 控制面可水平扩展，区域执行面故障不拖垮全局元数据服务。
  • 所有写操作幂等；状态通过声明式调谐而非单次远程命令维持。
  • Sandbox rootfs 默认短期；Workspace 数据与 Session 生命周期解耦。
  • 从第一天建立租户边界、审计、短期凭证和镜像供应链。

2.2 非目标

  • 不建设通用 IaaS、通用虚拟机管理平台或完整云厂商替代品。
  • 底座首轮不以 Windows Sandbox、GPU 多租户和跨 Region 实时卷迁移为目标。
  • 不让核心 Control Plane 主动持有客户服务器的长期 SSH 密码。
  • 不把 CubeSandbox、E2B 或 Daytona 作为底层强依赖；Daytona 仅用于产品与交互参考。
  • 不保证所有 Linux 软件在 gVisor 下无差异运行；RuntimeProfile 必须明确不兼容能力并 fail closed；回退不得静默降低用户所选隔离与网络策略。

4. 系统边界与上下文

6. User Web 与 Control Plane Web 的边界

User Web / Workspace UI

域名示例：app.example.com、workspace.example.com

  • 展示产品对象：Project、Workspace、Agent、Region、资源套餐、安全等级。
  • Terminal、Files、Git、Ports、Preview、Snapshots、Secrets、Usage。
  • 只调用 Public API，不可访问 Node、Cluster、Worker、RuntimeClass 等管理对象。
  • APP-M1 可复用现有 User Web 承载 Workspace/Agent UI；底座不以完整应用页面为启动前提。
Control Plane Web / Admin & Ops

域名示例：admin.internal.example.com

  • 管理 Region、ResourcePool、Cluster、Node、Worker、RuntimeProfile、Template、Image。
  • 执行 Drain、Disable、Reconcile、Force Stop、Quota Override、Incident 操作。
  • 强制 MFA、条件访问、VPN/Zero Trust、细粒度 RBAC 和完整审计。
  • 不得复用普通用户的公开 API Token；高风险操作按 07 Admin 要求 保留影响确认、资源名称/generation、Operation 和审计，Cleanup 确认不得省略。

6.1 推荐的部署与代码组织

项目建议理由
代码仓库可在同一前端 Monorepo共享 Design System、类型、API Client，但保持两个 App。
部署产物独立构建与发布管理员 Web 的漏洞或发布不应影响用户入口。
OIDC Client独立 Client ID / Audience避免 Token 可跨应用使用。
API/v1 与 /internal/v1 分离网关、WAF、网络和审计策略不同。
组件库共享 UI primitives，不共享业务路由保持视觉一致，避免权限逻辑耦合。

7.1 关键内部模块

Sandbox Manager
保存 DesiredState，推进 Session 状态机，处理幂等、重试、超时、补偿和垃圾回收。
Scheduler
过滤 Region/Runtime/KVM/合规/归属，再按容量、数据本地性、成本和亲和性评分。
Runtime Manager
把产品安全等级映射为 RuntimeProfile 和 RuntimePool，不让业务层出现 runsc/kata-fc 等实现名。
Workspace Manager
管理 Volume、Repo、Snapshot、Mount、数据保留和跨 Session 复用。
Node Manager
注册 Cluster/Node/Worker，维护 Capability、Capacity、Heartbeat、Drain 和版本兼容。
Policy Engine
统一处理 AuthZ、Quota、Runtime 许可、网络策略、Secret Binding 与企业规则。

7.2 OpenSandbox 集成策略

  1. 平台定义内部 SandboxRuntime 接口；先以固定版本 PoC 验证 OpenSandbox Adapter 的最小映射，不先造完整多后端抽象。
  2. 使用 OpenAPI 生成客户端，固定兼容版本；不让 User Web 直接调用上游 Server。
  3. 每个 RuntimePool 可部署独立 OpenSandbox Server 配置，例如 runc-pool、gvisor-pool、kata-pool。
  4. 上游缺失的多租户、计费、Remote Worker、SSH、区域调度在平台层实现，不深度 fork。
  5. 需要自研 Runtime 时实现相同内部接口；对用户 API 和 Workspace 数据模型保持不变。
待验证限制：固定 OpenSandbox 版本后核验 Secure Runtime 是否仅支持 Server 级配置。 在逐 Sandbox selector 未经证实前，不承诺同 Server 随意切换隔离 Runtime；需要时按 RuntimePool 拆配置，不预先深 fork。

8. 领域模型与状态模型

产品模型必须独立于 Docker Container、K8s Pod 或 MicroVM，否则底层切换会渗透到所有 API 和 UI。

8.1 关键对象

对象生命周期必须字段说明
Workspace长期org_id, project_id, region_policy, volume_id, template_id用户真正拥有的开发环境概念。
SandboxSession短期/可暂停workspace_id, desired_state, actual_state, runtime_profile, placement可多次创建；默认只有一个可写 Sandbox；多写挂载须有独立一致性方案，节点失联不等于旧写入者已 fencing。

RemoteWorker节点owner_scope, certificate, capabilities, heartbeat, version客户节点默认只承载该客户自己的 Workload。

8.2 Sandbox Session 状态机

REQUESTED
   └─→ SCHEDULING
        ├─→ PROVISIONING
        │    ├─→ STARTING ─→ RUNNING
        │    │                 ├─→ PAUSING ─→ PAUSED ─→ RESUMING ─┐
        │    │                 ├─→ STOPPING ─→ STOPPED            │
        │    │                 └─→ SNAPSHOTTING ──────────────────┘
        │    └─→ FAILED
        └─→ REJECTED

任意可终止状态 ─→ DELETING ─→ DELETED
异常状态必须保留 reason_code、retryable、last_transition_at 和 observed_generation。

8.3 数据库约束

  • 租户层次沿用本仓 Tenant → Organization → Project；所有租户对象须携带契约要求的 tenant/org/project 归属；所有请求必须在服务端解析 Tenant Context，禁止由前端自由传入并信任。
  • 主键推荐 UUIDv7；写请求带 Idempotency-Key；对象使用 version 做乐观锁。
  • 控制面 PostgreSQL 是元数据事实源；Redis 只用于缓存、短 Lease、限流，不作为生命周期事实源。
  • 关键跨服务事件使用 Transactional Outbox，消费者使用 Inbox/去重表保证至少一次投递下的幂等。

9. Runtime 与隔离设计

对用户暴露产品安全等级，对平台内部映射为 RuntimeProfile。避免在用户 API 中永久出现具体实现名。

产品等级内部 Runtime适用主要代价阶段
StandardDocker/runc 或 K8s/runc个人、可信代码、低成本任务共享宿主内核，隔离最弱BASE-M0/M1，限可信负载
SecuregVisor/runsc一般多租户 Coding Agent系统调用、文件与网络 I/O 可能有开销；存在兼容性边界BASE-M4 能力验证
IsolatedKata QEMU / Cloud Hypervisor未知代码、企业租户启动与内存开销更高，需要 KVMBASE-M4 按可用能力验证
MicroVMKata Firecracker；后续 Direct Firecracker高密度、强隔离、短任务镜像、网络、快照和 Guest Agent 工程复杂直接 MicroVM 后置
Full VMKVM/QEMU特殊内核、最高兼容、长期 Workspace密度低、启动慢、运维重按需
Firecracker 官方给出的 <125ms 是 VMM/Guest 启动能力，不等于“用户从点击到 Codex 可用”的端到端时间。 端到端还包含调度、镜像、卷、网络、Guest Agent、Repo 初始化和 Agent 启动，必须单独压测。

9.1 K8s RuntimeClass 映射

Kubernetes 的 RuntimeClass 用于按 Pod 选择 Runtime，适合把同一集群中的 runc、gVisor、Kata 映射为不同 RuntimeProfile。

# 概念示例：实际 handler 必须与 containerd/CRI 配置一致
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: secure-gvisor
handler: runsc
scheduling:
  nodeSelector:
    sandbox.example.com/runtime-gvisor: "true"
---
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: isolated-kata
handler: kata-qemu
scheduling:
  nodeSelector:
    sandbox.example.com/runtime-kata: "true"

9.3 Runtime 池化策略

  • BASE-M4：仅发布已验证的 Runtime 池。可信 standard-runc 与强隔离池分开；不支持所选隔离等级的节点必须拒绝调度，不要求每个 Region 预建所有类型。
  • 不同 Runtime 节点使用 taint/toleration 和 node label；不要假设所有节点配置同质。
  • 后续启用 Warm Pool 时，必须按 Runtime + Template + ResourceClass 拆分，避免错误复用。
  • Agent 模板要建立兼容矩阵：Codex/Claude Code、Docker-in-Docker、FUSE、ptrace、浏览器、语言工具链。

9.4 gVisor 的特殊处理

固定版本 PoC 需要核验 Egress Sidecar 的 NAT REDIRECT 与 gVisor netstack 兼容性，不能从本文推定已经支持。 因此本设计要求：gVisor 下的域名出网策略放到 CNI/节点/区域 Egress Gateway 层，不要依赖 Sandbox 内 iptables NAT。 可选实现包括 CNI FQDN Policy、显式 HTTP(S) Proxy、透明节点代理或平台 Credential Proxy。

11. 核心业务流程

11.1 创建 Workspace 与 Sandbox Session

11.2 SSH 连接流程

  1. User Web/CLI 向 Public API 申请指定 Workspace 的短期 SSH 凭证，服务端校验用户、组织、项目和 Session 权限。
  2. 平台签发 1～5 分钟有效的 SSH Certificate 或一次性 Access Token，principal 中只包含用户和 Session 范围。
  3. 客户端连接 ssh.example.com；全局入口根据 Session Home Region 路由至 Regional SSH Gateway。
  4. Gateway 验证证书、记录审计，随后通过内部 mTLS Tunnel 转发到 Sandbox 内 sshd。
  5. 为兼容 VS Code Remote SSH，建议保持真实 SSH 语义；不要仅把 SSH 命令翻译成普通 PTY。
  6. 客户 BYOC 节点不开放公网 SSH 给平台，Gateway 通过 Worker 已建立的反向 Tunnel 到达 Sandbox。

11.3 Remote Worker 注册流程

1. 已授权管理员经专用 CLI/API 获取一次性、短有效期 Enrollment Token（no-store）；Admin Web 只显示非敏感注册状态/指引，不显示或回读 Token
2. 客户节点安装 sandbox-worker
3. Worker 本地生成密钥对并提交 CSR + Enrollment Token
4. Worker Gateway 校验归属，签发短期 mTLS 证书
5. Worker 建立 outbound HTTP/2 或 WebSocket 长连接
6. 上报：
   - OS / arch / kernel
   - CPU / memory / disk / GPU
   - Docker / containerd / K8s / KVM / gVisor / Kata
   - Region / labels / network reachability
7. Node Manager 将 Worker 标为 ONLINE，Scheduler 才可使用
8. 命令使用 command_id + lease_id + generation，Worker 必须幂等执行
9. 心跳超时：ONLINE → DEGRADED → OFFLINE；停止下发新任务
10. 恢复连接后进行全量实际状态对账，不盲目重放旧命令

11.4 Preview 端口流程

  • 用户发布端口后生成短期 Signed URL，例如 https://3000-sb_xxx.preview.example.com。
  • Preview Proxy 校验 Token、Session 状态、端口策略，再路由到区域 Gateway。
  • 默认私有；公开 Preview 必须显式开启，并允许设置到期时间、请求限流和审计。
  • 禁止预览宿主机、Worker 管理端口和本地 metadata 地址。

14.1 域名与入口

14.2 出网策略

  • 默认拒绝 RFC1918、宿主机网关、Kubernetes API、Control Plane DB、云 metadata service 和其他租户网段。
  • 按 Workspace/Template 定义域名和 CIDR allowlist；Git、包管理器和模型 API 使用预置策略。
  • DNS 必须走受控 Resolver，记录请求域名并防止 DNS rebinding。
  • 对模型 API Key、Git Token 优先采用 Credential Broker/Proxy 注入，Sandbox 内只出现占位值或短期 Token。
  • 网络策略不能只依赖应用层；至少同时存在 CNI/防火墙和应用 Egress Gateway 两层。

14.3 SSH Gateway 安全要求

  • 不支持密码登录；使用短期 SSH Certificate 或一次性 Token。
  • 证书 principal 绑定 user_id + org_id + session_id，Gateway 不接受用户自定义跳转目标。
  • 每次连接记录来源 IP、设备、目标 Session、证书序列、开始/结束、传输字节和结果。
  • 支持立即吊销 Session 与 Organization；Gateway 定期拉取撤销列表或在线校验。
  • 命令录制属于敏感能力，默认只记录元数据；如企业需要完整会话录制，应单独告知与授权。

15. 持久化、快照与数据生命周期

15.1 存储分层

数据介质生命周期备份

Workspace VolumePVC / Block / NFS / Ceph随 Workspace按套餐快照
Snapshot / TemplateObject Storage + Manifest长期/可回收跨 AZ，必要时跨 Region
日志 / TraceObject Storage / Loki / Tempo按保留策略生命周期规则
Control MetadataPostgreSQL长期PITR + 多 AZ

15.2 Workspace 挂载约定

/workspace              # 用户代码和长期文件：持久卷
/home/sandbox/.config   # 可选择持久化的 Agent 配置
/tmp                    # 临时数据：随 Session 删除
/opt/toolchains         # 模板镜像只读工具链
/run/secrets/...        # 短期 Secret，tmpfs，不进入 Snapshot

15.3 快照语义

  • Template Snapshot：系统镜像、依赖和工具链，可被多个 Workspace 复用。
  • Workspace Snapshot：用户卷时间点快照，用于恢复；不得自动包含明文 Secret。
  • Session Snapshot：Runtime 特定能力，可能包含 rootfs/内存；跨 Runtime 兼容性不保证。
  • BASE-M5 验收文件系统快照，不承诺进程内存无损恢复。
  • 跨 Region 恢复以 Object Storage 中的 Snapshot Manifest + 数据复制为基础，不依赖共享全局文件系统。

16.1 调度两阶段

Hard Filter

  • Provider Ownership
  • RuntimeProfile / KVM / arch
  • CPU/RAM/Disk/GPU

  • 可用容量与碎片率

  • 租户反亲和与故障域

16.2 容量模型

峰值并发 Session
= 日活用户 × 峰值活跃比例 × 人均并发 Workspace × 峰值系数

可调度 CPU
= 节点物理 CPU × (1 - 系统预留 - 安全余量) × 允许超卖系数

可调度内存
= 节点物理内存 - OS/Kube/Runtime 预留 - Runtime 固定开销 - 安全余量

建议：
- 内存默认不超卖，CPU 可按 Runtime 和客户等级有限超卖
- Region 至少保留 20%～30% 可用容量或配置自动扩容
- Kata/MicroVM 必须单独计入每 Sandbox 固定内存与 Guest 开销
- 容量告警依据 requests/leases，不只看瞬时 CPU 使用率

16.3 Warm Pool（规模化后续能力）

  • Pool Key：region + runtime_profile + template_digest + resource_class。
  • 维护 minReady、maxReady、targetHitRate、idleTTL；所有 Ready 实例必须经过镜像与策略校验。
  • 分配时重置文件系统可写层、网络身份、Secret、SSH Host Key 和 Agent 状态，防止跨租户残留。
  • Warm Pool 命中率、回收失败率和污染检测必须作为核心指标。

17. 安全设计与威胁模型

17.1 主要威胁

Sandbox Escape
恶意代码利用内核、Runtime 或配置逃逸到宿主机。
Lateral Movement
访问其他 Sandbox、数据库、K8s API、Worker 管理口。
Credential Theft
读取模型 Key、Git Token、云凭证、缓存和 Snapshot。
SSRF / Metadata
访问 169.254.169.254 或内部控制面服务。
Supply Chain
恶意镜像、依赖、Agent 插件、Bootstrap 脚本或 Worker 更新。
Control Plane Abuse
越权 Drain、强制挂载、日志读取、配额修改或租户切换。

17.2 基线控制

领域最低要求
Runtime非特权、非 hostPID/hostNetwork、禁止任意 hostPath、seccomp、最小 capabilities、只读基础镜像。
节点Sandbox 节点池与 Control Plane 节点池分离；KVM/gVisor/Kata 节点使用明确标签与 taint。
网络Default Deny、metadata block、受控 DNS、CNI Policy + Egress Gateway、Preview 默认私有。
身份OIDC、MFA、短期 Token、内部 mTLS、Worker 证书自动轮换。
Secret不进入镜像、日志和快照；优先 Broker 注入；按 Workspace/Endpoint 最小授权。
镜像Digest 固定、签名验证、SBOM、漏洞扫描、允许仓库列表、构建环境隔离。
审计管理员、SSH、Secret Binding、Node 操作、网络策略变更不可抵赖记录。

17.3 Runtime 选择原则

  • 不要把 gVisor/Kata 当成“有了就绝对安全”；隔离 Runtime 只是纵深防御的一层。
  • 高风险租户或工具链不兼容时，允许调度到专属 Kata/MicroVM/VM 池。
  • 数据库、负载均衡、对象存储等平台服务不应运行在用户 Sandbox 内。
  • 对浏览器、Docker daemon、内核编译、FUSE、ptrace 等高风险/高权限需求建立例外审批和专属模板。

  • Session 状态变化写入不可变 Usage Event；每 1～5 分钟生成 checkpoint，防止长 Session 丢尾。

21. 发布、升级与供应链

21.1 发布单元

  • Global Control Plane、Regional Plane、Worker、Sandbox Template 分开版本。
  • Worker/execd 协议声明 minSupportedVersion 和 feature flags，支持 N-1 滚动升级。
  • 先 Canary Region，再低风险 Region，最后企业/国内 Region。
  • Runtime 节点升级采用 Cordon → Drain → 验证 → 回池；运行中 Workspace 可按策略等待或迁移。

21.2 镜像供应链

  • 所有生产镜像使用不可变 digest；CI 生成 SBOM、漏洞报告和签名。
  • Admission/Runtime Adapter 校验签名和允许仓库，禁止普通租户使用任意特权模板。
  • 基础模板按 Agent/语言/Runtime 建兼容测试：启动、Exec、PTY、Git、Preview、Snapshot、Secret、网络。
  • Remote Worker Bootstrap 与自动更新包同样签名；更新支持分批、回滚和最低安全版本。

元数据PostgreSQL事实源、事务、PITR；Redis 不替代数据库。
缓存/Lease现有 PostgreSQL authority；缓存按需不把 Redis 设为起步依赖，不新增第二个调度/写入权威。
RuntimeOpenSandbox + 自研 AdapterDocker BASE-M0；K8s/强隔离 BASE-M4；Direct MicroVM 后置。
K8s 网络CNI NetworkPolicy；优先支持 FQDN 策略gVisor 出网策略避免依赖 Sandbox 内 NAT。
Secrets云 KMS/Secret Manager 或 VaultEnvelope Encryption、短期注入。
ObservabilityOpenTelemetry + Prometheus + Grafana + Loki/Tempo全链路统一 Resource Attributes。
IaCTerraform/OpenTofu + Helm + GitOpsRegion 模块化，避免手工漂移。
服务拆分原则：一开始不要把 User、Project、Billing、Workspace、Sandbox 各拆一个微服务。 先用清晰模块边界和事件契约建立模块化单体；只有当团队、流量或发布节奏产生真实压力时再拆。 Gateway、Controller 与 Worker 的独立部署由连接负载和安全边界决定，不作为文档调整或 BASE-M0 的预设工程量。

阶段底座交付同阶段必交付 Admin Web
