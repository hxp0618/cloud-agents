# Security

Do not report vulnerabilities in public issues. Use [GitHub private vulnerability reporting](https://github.com/hxp0618/cloud-agents/security/advisories/new), which is enabled for this repository, or contact the repository owner through an authenticated private channel.

## Security contact and response

Security DRI: [@hxp0618](https://github.com/hxp0618), the repository owner. Security reports are acknowledged and triaged within 3 business days when the private reporting service is available. The triage records the affected release-candidate or deployment digest, severity, affected versions, exploitability, and the smallest redacted reproduction.

When coordinated disclosure is needed, the DRI keeps the report private, agrees an embargo date with the reporter, and publishes a GitHub security advisory with the fixed version or digest when the fix is available. Affected candidate manifests are revoked or superseded, a minimum accepted version is stated, and credential or signing material is rotated when the report requires it. If no embargo is needed, the advisory and fix are published after validation.

Never attach credentials, captured traffic, private source, account data, or unredacted runtime logs to a report. Include the affected release-candidate digest and the smallest redacted reproduction possible.

The [foundation security acceptance](docs/plan/cloud-agents-platform/05-gates-and-acceptance.md) covers tenant authorization, workspace ownership and deletion, single-writer fencing, access tokens, actual network enforcement, runtime isolation, and customer-node enrollment/revocation. A trusted single-tenant Docker profile is not proof of hostile multi-tenant isolation. Non-root, capability drops, and read-only rootfs are useful controls, not substitutes for a qualified isolation runtime. A customer-controlled host remains trusted for its own workload; enrollment does not conceal workload data from its host administrator.

Persistent Workspace/Volume deletion is distinct from Sandbox/Lease cleanup. Preserve the Admin Cleanup resource-name and generation confirmation; it is a product interaction requirement, not confirmation for every development action.

## IDENTITY-V1 security rules

These rules accompany the [built-in identity service decision](docs/plan/adr/0033-built-in-identity-service.md). The owner approved ADR-0033 and the linked P0 policies on 2026-10-08 and requested implementation through the IDENTITY-V1 Goal. These are required behavior, not a claim that implementation or acceptance is complete.

### Browser sessions and tenant tokens

- Admin Web and User Web use different `__Host-` cookies and session records. Cookies are `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, and have no `Domain`. Each record is bound to its application purpose; issued tokens retain the distinct existing Admin/User Control Plane audiences and also bind the application purpose in `client_id`. Either application rejects the other application's session. Production deployments use distinct HTTPS host origins because cookies are not isolated by port.
- The browser receives no bearer or tenant access token. A cookie contains only a cryptographically random opaque session identifier; the identity store owns the durable session record and retains only the identifier's hash. Sessions expire after 30 minutes idle or 12 hours absolute, rotate after login and reauthentication, and are revoked on logout. Revocation, account disablement, and credential reset reject new request admission after the revocation commit; already admitted mutations are not retroactively undone. The web server owns cookie issuance, the session proxy, and only a derived tenant-token cache.
- The web server exchanges an active session for a tenant-bound token and renews the proposed 15-minute token before expiry. The identity service records `jti` to user, session, tenant, and client. On every authorized request the Control Plane checks that record and current user, session, and role bindings without positive caching, and fails closed when validation is unavailable. User Web additionally requires active membership in the selected tenant. Admin Web requires either active tenant membership with the needed tenant role or an active `platform.admin` binding with an explicit, finite permission for the selected tenant. A stream checks before admission, at heartbeats no more than 15 seconds apart, and before each new authorized action; failure or revocation closes it.
- CLI browser login creates its own revocable human login grant, with seven days idle and 30 days absolute expiry. Each CLI token checks the current grant, user and role bindings; browser logout and CLI logout end their respective sessions. Password changes, resets and global account disablement also invalidate CLI access. Service-account tokens check their own active account, credential and current permissions; they do not create browser sessions or replace workload identity. The machine-only `remote-worker-bootstrap.act` scope is added only to an Admin-purpose, exact-project `cloud-agents-automation` token whose current RBAC decision includes `projects.act`; browser tokens, human CLI grants, User-purpose tokens and tenant-level tokens never receive it.
- Every state-changing browser request must present an exact allowed `Origin`; a missing, opaque, or mismatched origin is rejected. The session cookie's SameSite policy is defense in depth. If a form or client also uses a CSRF value, it is unpredictable, session-bound, checked server-side, and conveys no authentication authority. An OAuth authorization response is the only cross-site exception and must validate the exact redirect URI plus single-use `state`, PKCE verifier/challenge, and OIDC `nonce` before changing session state.
- Provider flows additionally use application-specific `__Host-` HttpOnly cookies for a 10-minute flow binding and a 5-minute, single-use reauthentication proof. Neither proof is returned in browser JSON or stored by application JavaScript. The callback checks the flow cookie in constant time, accepts only the closed provider query contract, and redirects to a fixed local path without credentials. Password login, logout, reset, and password enablement clear obsolete flow and reauthentication cookies. Provider client secrets and optional trust roots resolve through operator-configured file-reference allowlists; they are never accepted as raw values from provider configuration requests.
- CLI authorization uses a separate five-minute HttpOnly flow cookie and explicit approval by the current browser session, with exact Origin and session-bound CSRF checks. The approval is a native form submission; the server redirects its one-time code only to `http://127.0.0.1:<port>/callback`, with ports 1024–65535, state and PKCE. Only a document with a pending private CLI flow and the fully validated approval redirect permit that loopback form destination in their CSP. The CLI exchanges the code through the same Web origin; machine credential routes reject browser cookies, Origin and Fetch Metadata headers. The browser SDK receives neither the code nor the CLI grant. CLI grants are stored only in local owner-only files, never in arguments or browser storage.
- Session and credential-exchange responses use `Cache-Control: no-store`. Callback, invitation, and reset pages use `Referrer-Policy: no-referrer`, omit third-party resources, redact request URLs in access logs, and replace the proof-bearing URL immediately after exchange. Return destinations are limited to validated application-local paths; no caller-controlled external redirect is accepted.

### Passwords, recovery, and abuse controls

- Passwords accept 15–128 Unicode characters without silent trimming or truncation. The proposed Argon2id baseline uses a unique random salt, at least 19 MiB memory, two iterations, and one lane; P1 may select measured stronger parameters while keeping interactive login within its latency budget. Password and recovery plaintext is never stored or logged.
- Login uses distributed account and source-IP counters. The proposed default locks an account for 15 minutes after 10 failures in 15 minutes and denies an IP for 15 minutes after 100 failed attempts in 15 minutes; neither block is permanent, and P1 may calibrate these finite values before shipping. Responses and observable timing do not reveal whether an account exists. A forwarded client IP is accepted only from an authenticated, explicitly configured reverse proxy; otherwise the socket peer is used.
- Invitations and password-reset links contain independent, high-entropy, one-time values. Only their hashes are stored; invitations expire after 24 hours and reset links after 30 minutes. Both have an attempt limit, atomic consume operation, and replay rejection. Expiry, replacement, account disablement, or successful use revokes the value.
- An invitation may create the named account only after its verified email matches the invitation. Link possession proves email control only when an administrator has verified the delivery channel and ownership; omitting SMTP does not waive verified-email matching. An existing account accepts while authenticated, and a link never resets, replaces, or merges that account. Login, invitation acceptance, and recovery never merge accounts merely because email addresses match. Linking or unlinking a login method requires a current session plus reauthentication of the affected identity. The last usable login method and the last active platform administrator cannot be removed or disabled without a replacement.

### Tenant and provider trust boundaries

- A tenant administrator may invite members, assign tenant-scoped roles, and suspend that tenant's membership. Only a platform administrator may disable an account globally or issue an administrator-generated credential-reset link; one tenant administrator cannot disrupt the same person's access to another tenant.
- Email suffixes restrict admission and grant no membership or role. A verified email's complete domain is matched case-insensitively and exactly, without wildcard or textual suffix matching, when an invitation is issued, accepted, and converted into membership. A policy change does not silently remove existing members; an administrator must suspend them explicitly. A platform administrator is personally exempt from the domain restriction, but still needs an invitation, verified email, and explicit membership to join a tenant in User Web; this cannot exempt another account.
- OIDC discovery, authorization, token, user-info, JWKS, and Web redirect endpoints are exact configured trust boundaries and use validated HTTPS endpoints. A supplied authorization-response issuer is accepted for OIDC or GitLab only when it exactly matches the pinned provider issuer; GitHub accepts only its fixed OAuth callback issuer `https://github.com/login/oauth` while the resulting identity remains pinned to `https://github.com`; other providers reject this parameter. P5 CLI login may use an ephemeral HTTP callback bound only to a loopback address with state and PKCE checks, never an externally reachable listener. OAuth client secrets and other provider credentials are secret references, never plain configuration values. Provider claims do not automatically become verified email, identity links, membership, or roles. Any non-standard provider email trust is explicit per provider configuration and constrained to the configured tenant or enterprise account.
- The identity issuer and JWKS URL are pinned configuration fetched over validated TLS; token headers and claims cannot select a URL or trust root. Refresh is automatic but bounded, preserves immutable `kid`-to-key lineage, and fails closed after the last trusted snapshot expires or refresh validation fails. Signing-key freshness and lineage are separate from live session, `jti`, user, membership, and role revocation checks.

### Audit and later controls

- Creating, rotating, or disabling a service account requires a verified human Admin identity and current permissions. An automation service account cannot perform these actions, even with an administrative role. Both human and service-account denials retain the verified actor; unavailable denial persistence returns 503 before a success or forbidden response can escape.
- Authentication, session, invitation, reset, identity-link, membership, suffix-policy, provider, and authorization decisions emit audit records with time, action, actor, target, tenant, decision, reason code, and correlation ID. Audit data excludes passwords, cookies, raw tokens, authorization codes, provider secrets, private keys, and invitation/reset values or URLs. Security tables may contain one-way hashes needed to validate opaque values, and encrypted backups may contain security records; neither is audit output, and backup keys remain separate.
- Multi-factor authentication with TOTP or WebAuthn and user-visible active-session revocation are later work and are not implied by IDENTITY-V1.

## Runtime and release security

The Agent runtime treats the host environment as a trust boundary. New integrations should use `extendEnvironment: false`, anonymous credential descriptors, and the `CLOUD_AGENT_*` names. Portable and legacy aliases with different values are rejected. `bun run secret:scan` scans tracked and non-ignored untracked worktree entries plus `HEAD` by default; CI sets `CLOUD_AGENT_SECRET_SCAN_BASE` and scans the revisions in that base-to-head range. The scheduled security workflow sets `CLOUD_AGENT_SECRET_SCAN_ALL_HISTORY=1`; that mode uses the same case-insensitive candidate semantics as the final Git grep to select commits that introduce or remove matching lines, then scans those refs-reachable revision trees. The scanner reports redacted findings and stable coverage counts before success or failure. Only explicit synthetic test paths in `.secret-scan-allowlist.json` are excluded.

The repository scanner covers worktree text and refs-reachable commit-tree text. Its coverage record distinguishes tracked, untracked, enumerated, text, allowlisted, binary, and deleted worktree entries, and reports reachable, pickaxe-candidate, and scanned revision-tree counts for all-history mode. Ignored files, commit and tag messages, direct tree refs, unreachable objects, and content classified as binary are outside this scan. Use a dedicated object or credential-store audit when those scopes are required.

Deployment-target credentials are deployment-owned files referenced by `credentialRef`, with one write-only exception: an Admin may register a Kubernetes target from a kubeconfig. The browser parses it in memory and submits only the selected context's HTTPS server, embedded CA, and either a bearer token or an embedded client certificate and key. `exec`, `auth-provider`, file references, basic auth, `insecure-skip-tls-verify`, and `proxy-url` are rejected. The Control Plane seals the credential with AES-256-GCM under the operator key file `CLOUD_AGENTS_PLATFORM_TARGET_CREDENTIAL_KEY_FILE` (32 bytes, owner-only), binds the ciphertext to the tenant, project, and target, and stores it in tenant-isolated Postgres. Idempotency uses a keyed HMAC, never a plain hash of the credential. No API, audit event, log, or error returns it. Without the key, kubeconfig registration is refused, and existing sealed targets fail closed instead of falling back to same-named credential files.

The gitleaks current-tree scan uses `.gitleaks.toml`, whose entries are explicit synthetic fixture or generated-profile paths. Local ignored credential files are not repository evidence and must never be committed.

GitHub release-candidate artifacts are not npm releases and carry no GA security-support promise. A real authenticated provider test remains required before production use of Agent-enabled features. A foundation-only deployment instead requires its no-Agent lifecycle/access/isolation/recovery acceptance; neither test path grants production deployment or publication approval.
