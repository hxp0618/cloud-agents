# 10 · 路线图与待决策项

含分阶段路线图、MVP 定义、风险与缓解、需用户拍板的关键决策（附建议）、成功指标。

---

## 1. 分阶段路线图

> 原则：**先打通"沙箱内 pi 经 RPC 跑起来 + SSE 看得见 + 经 Gateway 用模型"的最小闭环，再叠治理、能力、隔离强化、多端。** 每阶段都端到端可用、可演示。

| 阶段 | 目标 | 关键交付 | 覆盖需求 |
|---|---|---|---|
| **P0 基础闭环 (MVP)** | 单 Agent 在 Docker 沙箱内经 RPC 跑通，Web 实时可见 | `@polaris/pi-rpc`（含行分割器）+ RPC 驱动器；Docker 沙箱后端；平台扩展（仅事件上报）；LLM Gateway（单/少数 provider）；最小登录 + 组织/项目；Web 工作台（对话+事件流+Diff）；Run + SSE API | 1、7、9（基础）、11（Web） |
| **P1 治理核心** | RBAC + 中央目录 + 工具策略闸门 + 审计 | 四级作用域 + 角色权限；Catalog（Agent/模型定义 + 可见域继承锁定）；平台扩展加**权限闸门**（allow/deny/ask + 审批往返）；模型白名单；审计日志；管理控制台 | 4、5、6（管理侧）、10 |
| **P2 能力层** | MCP + Skill + 子 Agent | **集成并治理 `pi-mcp-adapter`**（注入配置、调用过闸门、破坏性工具审批）；中央 Skill 库挂载（渐进式披露）；**集成并治理 `pi-subagents`**（权限子集、独立上下文、运行树、配额护栏） | 2、3 |
| **P3 市场与安全评估** | 用户创作 Skill + 发布安审 | Skill 创作编辑器；发布状态机；自动扫描（静态+能力清单核对+LLM 风险判定+依赖治理）；人审工作流；版本不可变 + 撤销熔断；运行时能力清单强制 | 6（核心差异化） |
| **P4 隔离强化与计量** | 强隔离 + 配额计费 | microVM/gVisor 后端；egress 出网白名单；资源配额 + 墙钟超时 + 崩溃恢复；信用计量 + 预算告警；安全监控消费者 | 8、9（计量/安全） |
| **P5 多端与生态** | 桌面/CLI/SDK + 集成 + 规模化 | 桌面端（Tauri，含本地目录桥接）；CLI；TS/Python SDK；IDE/Slack/CI 集成；HA/多区/预热池；SSO/SCIM/MDM | 11、10（规模化） |

> 阶段可并行裁剪：若优先验证差异化，可在 P1 后插入 P3 的"安审"骨架做 PoC。
>
> **复用红利**：P2 因复用 `pi-mcp-adapter`/`pi-subagents` 官方包，工作量主要在"治理与集成"（注入配置、过闸门、配额、运行树、事件），而非从零实现 MCP 客户端与子 Agent 编排——显著缩短 P2。

## 2. MVP（P0）验收标准

- [ ] 用户登录组织 → 选一个预置 Agent → 发起任务。
- [ ] 后端在 Docker 沙箱内以 `pi --mode rpc` 启动 pi，加载平台扩展。
- [ ] Agent 能 read/write/edit/bash 操作沙箱工作区（如克隆仓库、改文件、跑命令）。
- [ ] 模型调用经内部 LLM Gateway（密钥不暴露给客户端）。
- [ ] Web 工作台经 SSE 实时显示事件流、流式文本、文件 Diff、终端输出。
- [ ] Run 结束产物与会话 JSONL 同步到对象存储；沙箱回收。
- [ ] 全程事件进入事件日志（为后续审计/计量打底）。

**MVP 明确不含**：完整 RBAC（先用粗粒度）、MCP、Skill 市场、安审、microVM、计量计费、桌面端。

## 3. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **pi RPC/扩展 API 细节与文档有出入** | 集成返工 | 实施前对照 pi 源码核定，固化 `@polaris/pi-rpc` 类型；订阅 pi 版本变更；优先用文档高可信部分 |
| **`pi-mcp-adapter`/`pi-subagents` 的工具调用是否都经 `tool_call` 钩子未确认** | 若绕过钩子，则权限闸门/审计有缝隙 | **P2 启动前先验证**：装包跑通后核对其工具/派生路径是否经 `tool_call`；若否，在其集成点补挂拦截或与上游协作 |
| pi / 官方包升级破坏兼容 | 平台扩展或集成失效 | 锁版本（精确版本 + min-release-age）+ 升级回归测试；改动尽量回馈上游减少私改 |
| **用户 Skill 安全**（任意脚本） | 越权/数据外泄 | 三层信任边界（Skill≠Extension/官方包）+ 安审流水线 + 运行时能力清单强制 + 内核沙箱兜底 |
| 提示注入绕过策略层 | 危险操作被放行 | 双层防御：内核沙箱 + 出网白名单不依赖模型自觉；破坏性操作默认 ask/deny |
| 沙箱冷启动延迟 | 体验差 | 预热池 + 镜像分层缓存 |
| 多租户资源争用 | 邻居噪声 | 一 Agent 一沙箱 + 硬配额 + 故障域隔离（OpenHands 教训） |
| 成本失控 | 账单爆炸 | LLM Gateway 计量 + 配额/预算告警 + 墙钟超时 |
| MCP/子 Agent 递归爆炸 | 资源耗尽 | 复用 `pi-subagents` 递归护栏 + 叠加平台 深度/扇出/并发/超时上限 |
| 数据驻留/合规 | 法务阻塞 | 自托管/VPC 优先；敏感项目走私有/自建模型；ZDR 选项 |
| 安全威胁（提示注入/沙箱逃逸/供应链等） | 数据泄露或系统被控 | 详见 [11](./11-security-and-threat-model.md) 威胁模型与安全控制矩阵 |
| 测试覆盖不足导致安全漏洞上线 | 生产事故 | 详见 [12](./12-testing-strategy.md) 安全测试用例集与 CI 门禁 |

## 4. 待决策项（需用户拍板，附建议）

| # | 决策点 | 选项 | 建议 |
|---|---|---|---|
| D1 | **部署形态** | 单企业自托管/VPC ↔ 托管 SaaS 多租户 | **先单企业自托管/VPC**（契合"企业统一管理、不依赖本地、数据驻留"）；SaaS 作后续扩展 |
| D2 | **控制面语言** | 全 TypeScript(NestJS) ↔ 控制面 Go + 运行 Worker Node | **全 TS** 以复用 pi 生态与类型；除非团队 Go 实力强且需极致网关性能 |
| D3 | **沙箱后端起点** | Docker(gVisor) ↔ 直接上 Firecracker/Kata | **P0 用 Docker+gVisor**；P4 再按敏感度引入 microVM |
| D4 | **MCP / 子 Agent 实现** | **复用官方包 `pi-mcp-adapter`/`pi-subagents` + 治理** ↔ 自建 | **复用 + 治理**（官方包已成熟，省去造轮子；接口对齐 MCP/Agent Skills 标准，未来易迁移）；前提是 D-验证：其工具调用经我们的闸门 |
| D5 | **是否 fork pi** | 依赖消费 ↔ fork | **依赖消费 + 平台扩展 + 受控官方包**，改动回馈上游；避免维护分叉 |
| D6 | **用户 Skill 是否允许带脚本** | 纯 Markdown 指令 ↔ 允许受扫描脚本 | **允许脚本但强制安审 + 能力清单 + 沙箱**；纯指令型可走快速通道 |
| D7 | **计量单位** | 仅 token ↔ token+沙箱时长归一信用 | **归一信用单位**（参考 Devin ACU），覆盖算力成本 |
| D8 | **品牌/代号** | 沿用 Polaris ↔ 自定义 | 占位代号，按需替换 |
| D9 | **合规目标** | 基线 ↔ SOC2/等保/数据驻留具体要求 | 请明确目标地区与认证，影响 D1/沙箱/审计设计 |

> 这些不阻塞写设计，但会影响 P0–P1 的具体技术选型，建议尽早确认 D1/D2/D3。

## 5. 成功指标（建议）

- **采用**：项目接入数、月活 Agent Run 数、共享资源（Agent/Skill/MCP）复用率（"零重复配置"是否兑现）。
- **效率**：开发者从"登录到首次有效产出"时长；任务一次成功率；人审 Skill 的平均时延。
- **安全**：被闸门/沙箱拦截的高危操作数；安审拦截的不合格 Skill 比例；零密钥泄露事故。
- **可观测**：事件流端到端延迟；审计可回放覆盖率（应 100%）。
- **成本**：单次 Run 平均信用成本；预算告警命中后超支率。

## 6. 下一步建议

1. 用户确认 D1/D2/D3（部署/语言/沙箱起点）与 D9（合规）。
2. 拉取 pi 源码 + 安装 `pi-mcp-adapter`/`pi-subagents`，**验证其工具调用是否经 `tool_call` 钩子**（决定 D4 与治理"零缝隙"），产出 `@polaris/pi-rpc` 与平台扩展骨架。
3. 安全评审阅读 [11](./11-security-and-threat-model.md)（威胁模型），对残余风险 R1–R8 做接受/缓解决策。
4. 实施 **P0 MVP** 端到端闭环并演示，同步搭建 [12](./12-testing-strategy.md) 中的 CI 门禁（单元+集成+安全基准）。
5. 据演示反馈进入 P1 治理核心。
